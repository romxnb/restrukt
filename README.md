# restrukt

Перебудовує застосунок у код, який людина може зрозуміти й підтримувати: видимі сценарії, визначені власники правил і стану, цілісні модулі, перевірена поведінка.

## Використання

| Задача | Claude Code | Codex |
|---|---|---|
| Створити план | `/restrukt:plan [обсяг]` | `$restrukt plan [обсяг]` |
| Спланувати й реалізувати завдання | `/restrukt:implement [завдання, спека чи URL]` | `$restrukt implement [завдання, спека чи URL]` |
| Реалізувати одну задачу | `/restrukt:apply [план] [задача]` | `$restrukt apply [план] [задача]` |
| Перевірити задум | `/restrukt:review plan` | `$restrukt review plan` |
| Перевірити зібрану систему | `/restrukt:review` | `$restrukt review` |
| Доопрацювати конкретний недолік | `/restrukt:refine [names або coupling] [обсяг]` | `$restrukt refine [names або coupling] [обсяг]` |
| Подивитися стан | `/restrukt:status` | `$restrukt status` |

Без режиму `$restrukt [обсяг]` створює план. Обсяг — застосунок, тека або модуль; без нього використовується розмова чи поточний проєкт. Кілька рівноправних застосунків потребують уточнення.

## Workflow

1. **Планувальник створює план.** Відновлює сценарії та неявні правила, відділяє факти від гіпотез, незалежно проєктує модулі й гарантії. Пов'язує потрібний результат із правилом, рішенням, задачею та перевіркою. Кожна задача має контракт для нового виконавця. План перевіряється на сценаріях і залежностях; за потреби його переглядає незалежний помічник (`review plan`). Продуктовий код і тести не змінюються.
2. **Новий агент виконує одну задачу через apply.** Звіряє план з актуальним кодом, захищає поведінку перевіркою, реалізує й підключає результат, перевіряє використання, узгоджує назви та прибирає замінене. Передає стан наступному агенту й завершує виклик. Без назви продовжує незавершену задачу або бере першу доступну; незавершені залежності автоматично не виконує.
3. **Зведення входить у задачу плану.** Після інтеграції узгоджуються рішення, словник, дерево й залежності, видаляються зайві шари, старі поняття та мости.
4. **Новий рев'ювер перевіряє ціле.** Читає фактичний код і загальний diff, перевіряє наскрізну поведінку та взаємодії між задачами. Реалізацію не змінює; доведені знахідки стають новими задачами виправлення для `apply`, а завершені задачі не відкриваються. Після виправлень перевіряється змінене та його вплив. Готовність усіх задач і «Перевірка цілого» — окремі стани.

Після плану та після останньої задачі черги агент за ризиком вирішує, чи потрібен незалежний помічник для `review plan` або `review code`; умови описує [незалежний перегляд за потребою](skills/restrukt/references/auto-review.md). Пропуск записується як самоперевірка з причиною. Автоматичне коло одне: перегляд, виправлення, перевірка зміненого; після нього наступний `review` обирає користувач. `review` у новому чаті можна викликати будь-коли; сам цей режим агента не створює. Автор може зробити самоперевірку з явним позначенням цього факту. Обов'язкових хвиль помічників немає.

## Реалізація завдання

`implement` працює із завданням, а не лише з наявним кодом. Завдання задається текстом у промпті, шляхом до спеки (файл або тека) чи посиланням (URL, GitHub issue).

1. Агент читає завдання, досліджує зачеплений код і записує критерії приймання в план `docs/restrukt/<назва>/`.
2. Невідоме, що впливає на результат, виносить одним пакетом питань. Якщо потрібен доменний експерт, це може стати цілою сесією питань.
3. Проєктує зміну за тими самими принципами. Наявний код переробляє лише там, де без цього нова поведінка ляже криво; інші недоліки записує як можливі доопрацювання. Чи потрібен незалежний перегляд плану, агент вирішує сам.
4. Виконує чергу одразу або показує план і питає спосіб — умову визначає [implement](skills/restrukt/references/implement.md): покроково через `apply`, усе самостійно (зокрема з помічниками, коли доречно) або оркестрація — новий помічник на кожну задачу. Спосіб можна назвати одразу в промпті.
5. Кожна задача проходить цикл `apply`: спершу перевірка критерію, що падає, потім реалізація. Після останньої задачі (в `implement` або в покроковому `apply`) агент вирішує, чи потрібен незалежний `review code`; знахідки виправляються одним автоматичним колом.

Інші плани `implement` не читає й не враховує. Коміти — лише за дорученням.

## План і самостійність

Робоча пам'ять — `docs/restrukt/<назва>/plan.md` та `log.md`: кожен обсяг має власну теку, тож кілька планів співіснують. Інші режими обирають план за назвою теки, обсягом або задачею; за неоднозначності уточнюють. План зберігає правила, рішення, контракти задач, залежності й стан. Журнал — фактичні результати та перевірки. Спільне знання описується один раз; задача посилається на потрібний контекст. Стани задач і «Перевірки цілого», їхні переходи й позначку закритого автоматичного кола визначає один розділ головного контракту — «Стан плану»; режими лише виконують переходи.

План пишеться для людини й агента водночас, за методикою [текст плану](skills/restrukt/methods/writing.md): угорі огляд стану й наступний крок, далі нумеровані розділи, довідка — в додатках. Задачі й рішення мають сталі ID (`T3`, `R1`), посилання всередині плану ведуть на заголовки, залежності й стани показують діаграми Mermaid. Підходи взято з Information Mapping, Diátaxis, Apple Style Guide і книг Manning; джерела — у методиці.

Поведінка, сумісність і явні обмеження користувача задають рамки. Агент може переглянути власне архітектурне рішення за новими доказами, оновивши залежні задачі; типи, функції й розташування файлів обирає самостійно. Погодження плану не фіксує всі деталі. Питання потрібне для невідомого продуктового результату чи дії поза дозволом. Коміт, публікація та міграція реальних даних потребують доручення.

Довідник режиму визначає порядок роботи, методики — прийоми й винятки, критерії — приймання, шаблони — пам'ять. Агент читає потрібне на поточному кроці. Тактичний дизайн застосовується під час написання коду й перевірки його використання.

## Вузькі доопрацювання

`refine names` застосовує [принцип назв](skills/restrukt/methods/naming.md) до всього заданого обсягу; той самий принцип діє в `plan`, `implement`, `apply` і `review`. `refine coupling` застосовує connascence й усуває один доведений недолік. Поведінка зберігається. Без наявного плану робочих документів не створює. Нова архітектура повертається як структурна задача; інші режими й фокуси не запускаються автоматично.

## Результат і витрати

Відповідь показує результат, де читати сценарій, суттєві рішення, фактичні перевірки, залишок і наступний крок; деталі — посиланнями. Незавершене та неперевірене називається прямо.

Агент досліджує код поступово, зберігає докази й не повторює підтверджений аналіз без причини. Помічники необов'язкові та отримують обмежені доручення. Бюджет включає аналіз, реалізацію, перевірку й усіх помічників. Виміряну економію, час і токени можна повідомляти лише за наявності даних.

## Встановлення

Claude Code:

```text
/plugin marketplace add romxnb/restrukt
/plugin install restrukt@restrukt
```

Codex, із кореня локального клону:

```sh
codex plugin marketplace add ./
```

У Plugins Directory вибери marketplace `restrukt` і встанови плагін.
