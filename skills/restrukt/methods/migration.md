# OORP: перевірити поведінку й замінити частину

Коли: перед першою зміною реалізації та під час переходу на нову. Вхід: потрібний результат частини, поточний код, цільовий інтерфейс. Вихід: підключена нова реалізація з доказами перевірки.

## Дії

1. Запусти перевірку через межу, доступну реальному викликачу. Якщо її немає, створи захисний тест або відтворюваний сценарій до переписування. Покрий важливі результати, відмови та ефекти; тести не повинні залежати від приватної структури.
2. Відділи початкові падіння й відомі помилки від поведінки, яку зберігаєш. Виправлення помилки спирається на вимогу або рішення користувача.
3. Заміни цілісну частину осмисленими перевірюваними змінами. За потреби введи тимчасовий міст зі старого інтерфейсу й назви умову його видалення.
4. Підключи новий код до справжніх входів і викликачів. Повтори перевірки результату та інтеграції; порівняння зі старою реалізацією доречне лише для поведінки, яку зберігаєш.
5. Перевір використання старого коду, реєстрацію й конфігурацію; прибери замінене та повтори зачеплену перевірку. Невідключений старий шлях залишається роботою в плані.

## Приймання

Перевірки проходять через нову реалізацію й здатні виявити втрату результату або ефекту. Старий шлях прибраний або має явну незавершену причину існування. Недоступну перевірку не зараховуй як успішну.

## Приклад

До: тест прив'язаний до приватного `calculate()` старого сервісу.
Після: через `placeOrder()` перевірено суму, резерв і зняття резерву при відмові. Після заміни сервісу ці самі перевірки підтверджують потрібні результати.

Не переписуй весь застосунок до першої перевірки й не вимагай повного покриття всього репозиторію перед першою частиною.

Вибрано з [Object-Oriented Reengineering Patterns](https://scg.unibe.ch/assets/archive/books/OORP-2013-11-27.pdf): Write Tests to Enable Evolution; Test the Interface, Not the Implementation; Migrate Systems Incrementally.
