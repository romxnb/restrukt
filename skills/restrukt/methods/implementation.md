# Тактичний дизайн

Коли: обираєш форму зміни в `plan` і `implement`, пишеш код у `apply`, переглядаєш diff у `review code`. Вхід: поведінка, правила, наявний код, викликачі й тести. Вихід: найменше коду й понять, що дають потрібну поведінку, читаються з першого разу й захищають правила.

## 1. Типова форма

Нове має ту форму, яку йому дають фреймворк і сусідні фічі проєкту: ті самі теки, види класів і прийоми. Перш ніж проєктувати, знайди найближчу схожу фічу — вона зразок розкладки. Для стеку прочитай його довідник: [Symfony](stacks/symfony.md), [Vue](stacks/vue.md); він конкретизує цей розділ.

Правило живе в класі, що вже тримає його дані: метод сутності чи переліку, метод репозиторію для вибірки, суми й наявності. Дія контролера чи консольної команди переводить вхід у виклик і результат у відповідь; короткий намір з одним входом може читатися в ній цілком, а сценарій із кількома правилами чи залежностями — пошта, годинник, кілька репозиторіїв — живе в сервісі, який кличе дія. Засоби фреймворку й встановлених бібліотек — пошта, годинник, HTTP-клієнт, валідатор, серіалізатор, перевірка доступу — уже є межами: інжектуй і клич їх напряму.

## 2. Новий тип — лише з підставою

Новий клас, інтерфейс, перелік, файл, компонент, composable чи store має хоча б одну підставу:

1. його вимагає фреймворк: контролер, сутність, репозиторій, DTO запиту, команда, обробник повідомлення, міграція, сторінка;
2. стан з інваріантом, який змінюють кілька операцій, або життєвий цикл;
3. поведінку кличуть щонайменше два незалежні місця, або їй потрібні залежності, яких немає у викликача;
4. є щонайменше дві реальні реалізації чи варіанти, що обираються під час роботи;
5. адаптер сторонньої системи, якої фреймворк не абстрагує;
6. ховає складність, більшу за свій інтерфейс: без нього викликач став би важким для читання.

Без підстави — метод наявного класу або приватний метод єдиного викликача. Тестованість підставою не є: підміняй на межах, які дає фреймворк і його тестові засоби. Майбутнє уявне використання — теж.

## 3. Не роби

| Замість | Краще | Коли навпаки |
|---|---|---|
| інтерфейс з однією реалізацією | конкретний клас через впровадження залежностей | дві реалізації або межа пакета |
| сервіс чи метод, що лише передає виклик | прямий виклик | — |
| контролер із правилами, листами й розбором запиту кількох сценаріїв | сервіс сценаріїв; дія лише переводить вхід і відповідь | коротка дія, що читається з одного екрана |
| клас команди й обробника для синхронної дії з одним входом | дія контролера й метод сутності | кілька входів, асинхронність або так уже влаштовано проєкт |
| DTO й мапер, що повторюють сутність | відповідь, зібрана з сутності в одному місці | контракт API суттєво відрізняється від сутності |
| тип-значення для даних, які перевіряють в одному місці | перевірка на вході | значення має власні операції й ходить між модулями |
| клас-обгортка над списком сутностей | метод репозиторію чи сутності | — |
| виняток на кожен статус відповіді | засоби фреймворку для «не знайдено» й «заборонено», один виняток порушеного правила | — |
| подія й слухач з одним синхронним споживачем | прямий виклик | кілька незалежних реакцій |
| обгортка над засобом фреймворку | сам засіб | — |
| власний розбір чи перевірка входу, яку вже робить фреймворк, заради відповіді на ввід, якого клієнт не надсилає | засіб фреймворку з його відповіддю | вимога прямо задає іншу відповідь |
| нова тека верхнього рівня чи шари Domain/Application/Infrastructure | розкладка фреймворку й проєкту | рішення `plan` з обґрунтуванням у плані |
| приватний метод на кілька рядків з одним викликачем | вбудований код | назва пояснює неочевидне |
| константа чи змінна для значення, зрозумілого на місці | значення на місці | правило, що повторюється, чи число без очевидного змісту |

## 4. Прийоми

1. **Рішення біля даних.** Викликач не читає чужий стан, щоб повторити правило: рішення й зміна стану — операція власника. DTO, конфігурація й прості дані поведінки не потребують.
2. **Стани й переходи.** Допустимі стани — перелік; переходи — методи, що перевіряють попередній стан. Обов'язковий порядок викликів ховай в операції. Змінний стан допустимий у явного власника.
3. **Чесний контракт.** Назва й сигнатура показують намір, ефекти й можливі відмови: `process(true, false)` неприйнятне, getter не мутує стан і не ходить у мережу. Помилки передавай ідіоматично для мови.
4. **Читається згори донизу.** Сценарій видно в одному місці: головний шлях — кроки з назвами наміру, відмови — ранніми виходами. Допоміжну функцію виноси, коли в неї є другий викликач або вона ховає нетривіальну деталь. Коментар пояснює причину чи обмеження словами предметної області, а не код; план, задачі й ID рішень у коді не згадуй — вони тимчасові.
5. **Хибний зразок не поширюється.** Новий код не повторює сусіднього шаблону, що порушує цю методику чи [назви](naming.md). В одному типі чи модулі — один шаблон: якщо новий код мусив би або повторити хибний шаблон, або стати поруч із ним другим, спершу вирівняй сусідні операції того самого типу окремим кроком зі збереженням поведінки. Ширше вирівнювання — доопрацювання. Прийнятний узгоджений стиль проєкту зберігай.
6. **Коректність на межах.** Право доступу — засобом фреймворку, id із запиту не довіряй без перевірки власника. Одна операція — одна транзакція, ефекти назовні — після запису; перевірка, що читає інші записи перед записом (залишок, перетин, унікальність), — у тій самій транзакції з блокуванням або обмеженням бази. Фільтр, сума й наявність — у запиті до сховища, без запитів у циклі. «Зараз» — з годинника проєкту. Гроші — точним типом. Інтерфейс показує завантаження, помилку й неактивну дію під час запиту.
7. **Інструменти проєкту.** Запускай налаштовані форматер, лінтер і перевірку типів на змінених файлах: нових зауважень немає. Нових інструментів і конфігурації без доручення не додавай.
8. **Тести як документація.** Тест проходить через справжній вхід засобами фреймворку і читається як сценарій: назва — ситуація й очікуваний результат, одна поведінка на тест. Одна перевірка на правило й на кожну його межу; ту саму поведінку не перевіряй на кількох рівнях. Власні класи не підміняй; спільну підготовку — функцією з назвою наміру в тому самому файлі.

## 5. Перевірка економії

Перед передачею результату й у `review code`:

1. Випиши нові файли й типи зі змін (`git status --porcelain`, `git diff --stat`) разом із новими публічними методами.
2. Для кожного нового типу назви підставу з розділу 2 одним рядком. Без підстави — вбудуй і повтори перевірки.
3. Для кожного рядка розділу 3 перевір, чи не з'явився такий шаблон.
4. У журнал — одним рядком: нові файли й типи з підставами.

Після інтеграції використання перевіряє [перевірка з боку викликача](caller-check.md).
