# Приймання структури

Застосуй після вибору цільової моделі й до завершення перебудови. Оцінюй новий код як самостійну систему: поліпшення відносно legacy недостатньо.

| Що має бути правдою | Як перевірити на коді |
|---|---|
| Сценарій можна прочитати | Від справжнього входу простежуються головні кроки, альтернативи й результат. Для асинхронного процесу явні передача події та власник продовження. Імена не приховують суттєвих ефектів. |
| Правила й стан мають власників | Для конкретного правила видно місце зміни та захист інваріанта. Викликач користується невеликим інтерфейсом і не мусить знати порядок приватних операцій. Розподілений стан має правила узгодження. |
| Залежності й ефекти явні | Логіка відділена від технологічних деталей; порядок ефектів і помилки визначені. Цикли не змушують модулі знати внутрішню будову одне одного. Нова абстракція прибирає конкретну залежність. |
| Нова реалізація працює | Справжні входи викликають новий код. Перевірки підтверджують результати, альтернативи й інтеграцію. Старий шлях прибраний або ще позначений незавершеною роботою. |
| Модель виведена незалежно | Для кожного нетривіального структурного рішення є щонайменше два варіанти, порівняні на репрезентативних сценаріях; якщо проста форма має одну природну декомпозицію, план пояснює це без штучної альтернативи. Збережені старі межі мають обґрунтування в обраній моделі, а не в поточному дереві. |
| Зміна має локальне місце | Для типової зміни правила або інтеграції видно основний модуль і обмежений набір споживачів; викликачі не повторюють рішення власника. |
| Модулі приховують складність | Публічний інтерфейс простіший за внутрішню реалізацію; правило, стан або технологічний ефект можна змінити без знання викликачів про приватний порядок дій. Шар, який лише передає виклик, має окрему причину існування. |
| Дерево відображає модель | Верхньорівневі папки мають зрозумілу роль і об'єднують те, що змінюється разом. Напрямки залежностей відповідають правилам системи, а механіка framework не визначає доменну модель. |
| Поняття економні й назви правдиві | Немає класів, інтерфейсів або шарів без окремої відповідальності. Назви папок, типів, функцій, параметрів і результатів узгоджені та показують намір і важливі ефекти. |
| Заміна завершена | Замінені класи, папки, назви, сумісні мости та дубльовані рішення видалені після перевірки споживачів; незавершене лишається в основній черзі. |

Проста функція може бути достатньою реалізацією сценарію. Межі визначають поняття, правила й причини змін. Кількість файлів, інтерфейсів або назва патерна не доводять якість; менша кількість сильніших понять часто зменшує складність.

Порушення цієї таблиці виправляється в основній перебудові. У необов'язкове доопрацювання може піти лише конкретне поліпшення, яке не порушує потрібну поведінку, читабельність сценарію та цілісність структури.
