# Критерії архітектури

Застосуй після вибору цільової моделі й до завершення перебудови. Під час планування перевір обґрунтованість рішень; під час реалізації — їхнє фактичне втілення. Оцінюй новий код як самостійну систему: поліпшення відносно legacy недостатньо.

| Що має бути правдою | Як перевірити на коді |
|---|---|
| Сценарій можна прочитати | Від справжнього входу простежуються головні кроки, альтернативи й результат. Для асинхронного процесу явні передача події та власник продовження. Імена не приховують суттєвих ефектів. |
| Правила й стан мають власників | Для конкретного правила видно місце зміни та захист інваріанта. Допустимі стани й переходи явні; для ресурсу відомо, хто завершує роботу при успіху, відмові та скасуванні, коли вони можливі. Розподілений стан має правила узгодження. |
| Бізнес-логіку знаходиш за словом | Для кожного рядка «Власників» і словника плану пошук назви в коді веде до одного місця визначення. Суть із [бізнес-логіки](../methods/business-logic.md) не продубльована й не обходиться: жоден запис стану не минає перевірки власника. Намір з одним входом може читатися в дії контролера чи команди. |
| Інтерфейс зрозумілий у використанні | З потрібних викликачів видно намір, результати й важливі ефекти операцій. Вони розрізняють потрібні наслідки та не підтримують інваріант через приватний порядок дій. |
| Залежності й ефекти явні | Рішення не змішані з протоколом і форматом даних; засоби фреймворку викликаються напряму. Порядок ефектів і помилки визначені. Цикли не змушують модулі знати внутрішню будову одне одного. |
| Нова реалізація працює | Справжні входи викликають новий код. Перевірки підтверджують результати, альтернативи й інтеграцію. Старий шлях прибраний або ще позначений незавершеною роботою. |
| Модель виведена незалежно | План містить докази вибору за [методикою проєктування](../methods/design.md). Збережені старі межі мають обґрунтування в обраній моделі, а переглянуті рішення враховують нові факти з реалізації. |
| Зміна має локальне місце | Для типової зміни правила або інтеграції видно основний модуль і обмежений набір споживачів; викликачі не повторюють рішення власника. |
| Модулі приховують складність | Публічний інтерфейс простіший за внутрішню реалізацію; правило, стан або технологічний ефект можна змінити без знання викликачів про приватний порядок дій. Шар, який лише передає виклик, має окрему причину існування. |
| Дерево відображає модель | Розкладка фреймворку збережена; власні теки мають зрозумілу роль і об'єднують те, що змінюється разом. Напрямки залежностей відповідають правилам системи. |
| Поняття економні й назви правдиві | Кожен новий тип має підставу з [тактичного дизайну](../methods/implementation.md#2-новий-тип--лише-з-підставою); немає інтерфейсів з однією реалізацією, шарів чи методів, що лише передають виклик. Назви відповідають [принципу назв](../methods/naming.md): одне поняття має одну назву всюди, слова прямі й правдиві. |
| Заміна завершена | Замінені класи, папки, назви, сумісні мости та дубльовані рішення видалені після перевірки споживачів; незавершене лишається в основній черзі. |

Проста функція може бути достатньою реалізацією сценарію. Межі визначають поняття, правила й причини змін. Кількість файлів, інтерфейсів або назва патерна не доводять якість; менша кількість сильніших понять часто зменшує складність.

Порушення цієї таблиці виправляється в основній перебудові. Зайвий новий тип, інтерфейс, шар чи публічна операція — теж порушення, а не доопрацювання. У необов'язкове доопрацювання може піти лише конкретне поліпшення, яке не порушує потрібну поведінку, читабельність сценарію та цілісність структури.
