# Зв'язаність: знайти спільну причину змін

Вхід: конкретне правило, формат або порядок дій, зміна якого зачіпає кілька місць. Вихід: менше прихованих домовленостей без втрати поведінки.

1. Назви зміну, яку важко зробити, і знайди місця, що мусять змінюватися разом. Підтверди адресами, споживачами або тестом; не виводь зв'язаність лише з однакового тексту.
2. Встанови домовленість: спільне значення, алгоритм, позиції даних або порядок виконання. Оціни кількість учасників, відстань між модулями й складність узгодження. Бали без вимірювання не вигадуй.
3. В обраній структурі зосередь спільне рішення в наявного власника або зроби приховану домовленість явним контрактом. Якщо потрібні нові межі чи власники, поверни структурну задачу.
4. Перевір, що всі споживачі користуються рішенням, і повтори поведінкові перевірки. Покажи на конкретній зміні, які місця більше не треба узгоджувати вручну.

Приймання: усунено доведену приховану залежність; виправлення не рознесло ту саму відповідальність ще далі. Дублювання різних бізнес-правил не об'єднане помилково.

Приклад: два викликачі повторюють формулу знижки → обидва використовують наявну `DiscountPolicy`. Якщо це різні політики продажу, однакові формули не є підставою злиття.

Прийом спирається на [connascence: strength, degree, locality](https://connascence.io/). Повний перепис типів зв'язаності для кожного рядка коду не потрібний.
