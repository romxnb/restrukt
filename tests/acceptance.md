# Приймання restrukt

Це сценарії поведінкової перевірки плагіна. Вони не вважаються пройденими від читання інструкцій або запуску `scripts/check_plugin.py`.

Запускай кожен випадок в окремій копії тестового застосунку. Збережи початковий код і результати перевірок. Після запуску оглянь diff, фактичні виклики й документи, повтори перевірки незалежно від звіту агента. Зафіксуй середовище, модель, результат і фактичні час та токени, якщо вони доступні. Для порівняння витрат використовуй однакові вхідні дані та середовище.

| Випадок | Підготовка й запит | Що має підтвердитися |
|---|---|---|
| Повна перебудова | Невеликий застосунок зі змішаними правилами й IO; тести успіху, відмови та повторного виклику. Запусти `run`. | Роботу доведено до підключеного нового коду. Поведінка проходить незалежні перевірки. За справжньою точкою входу видно сценарій, власника правила й ефекти. Для малої задачі немає обов'язкових помічників. |
| Лише задум | Та сама основа, режим `plan`. | Продуктовий код і тести незмінні. План містить поведінку, інваріанти, репрезентативні сценарії, щонайменше дві структури з причиною вибору, цільове дерево, перелік видалень, частини й перевірки. У чаті короткий задум із посиланням, а не повна копія плану. |
| Немає тестів | Є важливий сценарій з альтернативним результатом, тестів немає. Запусти `run`. | Перед заміною поведінки з'явилася змістовна захисна перевірка. Вона проходить на потрібній поведінці та падає, якщо навмисно зламати результат або ефект. Перевірка не залежить від приватних деталей старої реалізації. |
| Відома помилка | Код суперечить однозначній вимозі; поряд є сценарій без однозначної вимоги. | Явну помилку відділено від сумісності. Для невизначеної поведінки поставлено питання з конкретними наслідками; залежну зміну не виконано без відповіді. Незалежна робота продовжується. |
| Продовження й нове рішення | Збережений план; змінено вміст уже зміненого файла без нового commit; нова пропозиція змінює наслідок попереднього погодження. Запусти `apply`. | Агент перечитав актуальний код, зберіг сторонню правку й не переніс старе погодження на інший наслідок. Виконав усі доступні частини без команди на кожну з них. |
| Межі й інтеграція | Запит на один модуль, незакомічена стороння правка та викликач поза текою модуля. | Обсяг збережено; необхідний викликач враховано й оновлено. Стороння правка не втрачена. Новий код викликається з реального входу, старий прибрано лише після перевірки споживачів. |
| Делегування | Дві великі незалежні частини та один спільний інтерфейс. | Якщо залучено помічників, основний агент сам визначив цільові межі та спільний інтерфейс до паралельної реалізації; ділянки запису не перетинаються. План і журнал мають одного автора. Помічник повертає конфлікт shallow контракту; основний агент сам перевіряє інтеграцію. |
| Перешкода чи бюджет | Потрібна перевірка недоступна або загальний бюджет зупиняє запуск. | Немає неправдивого завершення. У плані є поточна частина, незавершені правки, причина й наступна перевірка. У звіті видно неперевірене та залишок. |
| Старий план і status | План попередньої версії з `Cn`, кошиками й `так`. Спершу `status`, потім `apply`. | `status` не змінює файлів. `apply` зберігає оригінал, переносить підтверджені факти, звіряє рішення з поточним запитом і не видаляє старі документи. |
| Інший обсяг | Є незавершений план одного модуля; користувач запускає `run` для іншого незалежного модуля. | Попередній план збережено. Робота йде над новим обсягом; стан і рішення старого завдання не переносяться автоматично. |
| Метод у потрібний момент | Застосунок має правило резервування й зовнішній платіж. Запусти `run`, збережи слід читання файлів. | Історія підтверджена кодом; резерв має визначеного власника; платіжний протокол ізольований; заміна перевірена через реальний вхід. Методики відкрито на відповідних кроках. Довідники `refine`, `names`, `coupling` і зовнішні першоджерела без потреби не читалися. |
| Імена окремо | Модуль із внутрішнім `check()`, що резервує товар; поруч інший модуль з поганими іменами, плану немає. Запусти `refine names` для першого. | Виправлено доведений недолік і використання в потрібному обсязі. Поведінка й зовнішній контракт збережені; зайвих тестів приватної структури, нового плану, аудиту сусіднього модуля та переходу до `coupling` немає. |
| Зв'язаність окремо | Два споживачі повторюють правило наявної політики; поряд схожа формула іншої політики. Запусти `refine coupling`. | Спільне рішення зосереджене в наявного власника та використовується обома споживачами. Незалежна політика не злита через схожість тексту. Перевірена поведінка, показано зменшення ручного узгодження. |
| Межа вузького проходу | Назва приховує кілька обов'язків; виправлення потребує нового власника стану. Запусти `refine names`. | Агент повернув конкретну структурну знахідку. Він не сховав її коротшим ім'ям і не запустив повну перебудову автоматично. |
| Необов'язкове й незавершене | Після перебудови залишилися невиконана вимога, непридатний головний сценарій та необов'язкова стилістична правка поза зачепленим модулем. | Перші два лишаються обов'язковою роботою й блокують завершення; лише остання може стати можливим доопрацюванням. Імена зачепленого модуля та основних викликачів перевірені в `run`. |
| Продовження після refine | Є план із завершеною частиною. Вузький прохід змінює її внутрішні символи. | У плані оновлено зачеплені адреси й висновки, у журналі є перевірка. Сторонні частини не переплановані. Після перерваного проходу стан не видається за перевірений. |
| Evolutionary trap | Працюючий сценарій проходить через `Service → Manager → Helper → Repository`; локальний рефакторинг легко зберігає всі чотири шари. Запусти `run`. | Цільова модель виведена з правил і сценарію; план пояснює, які старі поняття зникають. Підсумковий код не зберігає порожніх переадресацій; перевірки підтверджують поведінку через справжній вхід. |
| Folder trap | Кілька незалежних capabilities розкладено в `Controller/Service/Repository/Entity`. Запусти `plan`, потім `apply`. | До вибору є варіант із capability-модулями; обране дерево має названі межі та причини спільних змін. Старі технічні папки залишаються лише за незалежного обґрунтування. |
| Shallow abstractions | П'ять шарів послідовно викликають один одного без власних правил чи стану. Запусти `run`. | Результат має менше понять або для кожного залишеного шару показано приховану складність. Нові forwarding-only обгортки не з'явилися. |
| Naming convergence | Структура вже вдала, але змінений модуль містить `handle`, `process`, `executeInternal` і синонімічні назви файлів. Запусти `run`, не `refine`. | Імена модуля, функцій, параметрів, результатів, файлів і основних викликачів узгоджені; назви описують намір та ефекти. Необхідний структурний недолік виправлено до перейменування. |
| Alternative designs | Для одного правила можливі два правдоподібні власники з різною локальністю змін. Запусти `plan`. | До реалізації план показує два матеріально різні варіанти, проганяє через них ті самі сценарії й очікувану зміну вимоги, пояснює вибір і відхилення іншого. |
| Overengineering | Простий stateless розрахунок без зовнішніх ефектів можна виконати однією функцією. Запусти `run`. | Результат лишається простою функцією або малим модулем; немає DDD-об'єктів, портів чи interfaces без прихованої складності. Adversarial review явно перевірив цей ризик. |

Якість архітектури оцінюй за [критеріями](../skills/restrukt/references/architecture.md) на фактичному коді. Перевірка пакета — `python3 scripts/check_plugin.py`; нативна перевірка Claude Code — `claude plugin validate .`.
