# Приймання restrukt

Це сценарії поведінкової перевірки плагіна. Вони не вважаються пройденими від читання інструкцій або запуску `scripts/check_plugin.py`.

Повний цикл: `plan`, потім окремий `apply` для кожної задачі новим агентом, після зведення — `review` іншим агентом. У кожному виклику перевір межі режиму й передачу стану.

Запускай кожен випадок в окремій копії тестового застосунку. Для випадків стану плану є готова [фікстура](fixtures/plan-state/README.md): застосунок, сценарії плану й команда `claude -p`; її сценарій названо в колонці підготовки. Збережи початковий код і результати перевірок. Після запуску оглянь diff, фактичні виклики й документи, повтори перевірки незалежно від звіту агента. Зафіксуй середовище, модель, результат і фактичні час та токени, якщо вони доступні. Для порівняння витрат використовуй однакові вхідні дані та середовище.

| Випадок | Підготовка й запит | Що має підтвердитися |
|---|---|---|
| Повна перебудова | Невеликий застосунок зі змішаними правилами й IO; тести успіху, відмови та повторного виклику. Виконай повний цикл. | Роботу доведено до підключеного нового коду. Поведінка проходить незалежні перевірки. За справжньою точкою входу видно сценарій, власника правила й ефекти. Для малої задачі немає обов'язкових помічників. |
| Лише задум | Та сама основа, режим `plan`. | Продуктовий код і тести незмінні. План містить поведінку, інваріанти, репрезентативні сценарії, щонайменше дві структури для кожного нетривіального рішення або коротке обґрунтування простої природної форми, цільове дерево, перелік видалень, контракти задач і перевірки. У чаті короткий задум із посиланням, а не повна копія плану. |
| Немає тестів | Є важливий сценарій з альтернативним результатом, тестів немає. Виконай повний цикл. | Перед заміною поведінки з'явилася змістовна захисна перевірка. Вона проходить на потрібній поведінці та падає, якщо навмисно зламати результат або ефект. Перевірка не залежить від приватних деталей старої реалізації. |
| Відома помилка | Код суперечить однозначній вимозі; поряд є сценарій без однозначної вимоги. | Явну помилку відділено від сумісності. Для невизначеної поведінки поставлено питання з конкретними наслідками; залежну зміну не виконано без відповіді. Незалежна робота продовжується. |
| Продовження й нове рішення | Збережений план; змінено вміст уже зміненого файла без нового commit; нова пропозиція змінює наслідок попереднього погодження. Запусти `apply`. | Агент перечитав актуальний код, зберіг сторонню правку й не переніс старе погодження на інший наслідок. Виконав лише обрану задачу й передав наступну дію через план. |
| Межі й інтеграція | Запит на один модуль, незакомічена стороння правка та викликач поза текою модуля. | Обсяг збережено; необхідний викликач враховано й оновлено. Стороння правка не втрачена. Новий код викликається з реального входу, старий прибрано лише після перевірки споживачів. |
| Делегування | Дві великі незалежні частини та один спільний інтерфейс. | Якщо залучено помічників, основний агент сам визначив цільові межі та спільний інтерфейс до паралельної реалізації; ділянки запису не перетинаються. План і журнал мають одного автора. Помічник повертає конфлікт shallow контракту; основний агент сам перевіряє інтеграцію. |
| Перешкода чи бюджет | Потрібна перевірка недоступна або загальний бюджет зупиняє запуск. | Немає неправдивого завершення. У плані є поточна частина, незавершені правки, причина й наступна перевірка. У звіті видно неперевірене та залишок. |
| Старий план і status | План попередньої версії з `Cn`, кошиками й `так`. Спершу `status`, потім `apply`. | `status` не змінює файлів. `apply` зберігає оригінал, переносить підтверджені факти, звіряє рішення з поточним запитом і не видаляє старі документи. |
| Інший обсяг | Є незавершений план одного модуля; користувач запускає `plan` для іншого незалежного модуля. | Новий план створено в окремій теці `docs/restrukt/<назва>/`; попередній план і журнал не змінені. Стан і рішення старого завдання не переносяться автоматично. |
| Кілька планів | Є два плани в окремих теках. Виклич `apply` без назви плану й задачі, потім `status` без аргументів, потім `apply <план>`. | Перший `apply` уточнив план, не обравши його мовчки. `status` показав обидва плани без правок. Останній виклик виконав одну задачу обраного плану й змінив лише його `plan.md` та `log.md`. |
| План без теки | Є `docs/restrukt/plan.md` і `log.md` попередньої версії. Виклич `apply`. | Файли перенесено в `docs/restrukt/<назва>/` без втрати змісту, посилання оновлено; далі виконано одну задачу. |
| Метод у потрібний момент | Застосунок має правило резервування й зовнішній платіж. Виконай повний цикл, збережи слід читання файлів. | Історія підтверджена кодом; резерв має визначеного власника; платіжний протокол ізольований; заміна перевірена через реальний вхід. Тактичний дизайн прочитано перед написанням нової реалізації, після інтеграції перевірено її використання. Методика не завантажувалася під час планування. Довідники `refine`, `names`, `coupling` і зовнішні першоджерела без потреби не читалися. |
| Розкидане правило | Правило «одна активна підписка на клієнта» тримають унікальний індекс і перевірка у двох входах із трьох; третій покладається на помилку бази. Запусти `plan`. | До вибору структури план називає правило, усі місця, де його забезпечено, включно з індексом, і вхід без перевірки. Розбіжність без вимоги винесено в питання, а не виправлено мовчки. У цільовій структурі правило має одного власника. |
| Прихований стан | Життєвий цикл замовлення закодовано комбінацією `paidAt`, `shippedAt`, `cancelledAt` і `isDraft` без переліку статусів; модулі по-різному записують ту саму умову. Запусти `plan`, потім `apply`. | План називає неявний життєвий цикл, переходи та всі місця запису полів. Однакові за змістом умови в різному записі розпізнано як одне правило; схожі, але різні не злито. Після перебудови стан і переходи мають явне представлення й власника; переходи перевірено через справжні входи. |
| Вибіркове читання review | Збережений план і завершені задачі. Окремими агентами виконай `review plan` і `review code`, збережи слід читання файлів. | `review plan` не читав повні довідники `plan` чи `review-code` і тактичний дизайн; `review code` не читав `review-plan`, `handoff` і повний тактичний дизайн. Обидва виконали свої перевірки повністю. |
| Імена окремо | Модуль із внутрішнім `check()`, що резервує товар, образним `Showcase` і синонімами одного поняття; поруч інший модуль з поганими іменами, плану немає. Запусти `refine names` для першого. | Виправлено всі доведені порушення принципу назв і використання в потрібному обсязі, а не лише одне ім'я. Поведінка й зовнішній контракт збережені; зайвих тестів приватної структури, нового плану, аудиту сусіднього модуля та переходу до `coupling` немає. |
| Зв'язаність окремо | Два споживачі повторюють правило наявної політики; поряд схожа формула іншої політики. Запусти `refine coupling`. | Спільне рішення зосереджене в наявного власника та використовується обома споживачами. Незалежна політика не злита через схожість тексту. Перевірена поведінка, показано зменшення ручного узгодження. |
| Межа вузького проходу | Назва приховує кілька обов'язків; виправлення потребує нового власника стану. Запусти `refine names`. | Агент повернув конкретну структурну знахідку. Він не сховав її коротшим ім'ям і не запустив повну перебудову автоматично. |
| Необов'язкове й незавершене | Після перебудови залишилися невиконана вимога, непридатний головний сценарій та необов'язкова стилістична правка поза зачепленим модулем. | Перші два лишаються обов'язковою роботою й блокують завершення; лише остання може стати можливим доопрацюванням. Імена зачепленого модуля та основних викликачів перевірені в `apply`. |
| Продовження після refine | Є план із завершеною частиною й перевіреним цілим (фікстура `refine-verified`). Вузький прохід змінює її внутрішні символи. | У плані оновлено зачеплені адреси й висновки, у журналі є перевірка. Сторонні частини не переплановані. Після перерваного проходу стан не видається за перевірений. |
| Evolutionary trap | Працюючий сценарій проходить через `Service → Manager → Helper → Repository`; локальний рефакторинг легко зберігає всі чотири шари. Виконай повний цикл. | Цільова модель виведена з правил і сценарію; план пояснює, які старі поняття зникають. Підсумковий код не зберігає порожніх переадресацій; перевірки підтверджують поведінку через справжній вхід. |
| Folder trap | Кілька незалежних capabilities розкладено в `Controller/Service/Repository/Entity`. Запусти `plan`, потім `apply`. | До вибору є варіант із capability-модулями; обране дерево має названі межі та причини спільних змін. Старі технічні папки залишаються лише за незалежного обґрунтування. |
| Shallow abstractions | П'ять шарів послідовно викликають один одного без власних правил чи стану. Виконай повний цикл. | Результат має менше понять або для кожного залишеного шару показано приховану складність. Нові forwarding-only обгортки не з'явилися. |
| Прямі назви | Клас `Showcase` будує блок, який інтерфейс і тікети називають «Featured products»; модуль `FailedPaymentRecovery` бухгалтерія називає «dunning»; `spinUpTestDatabase`. Виконай `plan` і `apply`. | Назви стали словами інтерфейсу й домену (`FeaturedProducts`, `Dunning`) та буквальними дієсловами (`createTestDatabase`); усталені терміни на кшталт `RateLimiter` чи `ctx` не замінено. Словник плану містить обрані слова. |
| Одне поняття — одна назва | Те саме поняття зветься `Order`, `Purchase` і `Checkout` у різних модулях; обсяг охоплює лише частину. Виконай `apply` задачі цього обсягу; окремо `review code`. | Поняття має одне слово зі словника в усьому обсязі; поза обсягом наявну назву збережено й записано задачею, двох назв у коді обсягу немає. `review code` вважає синоніми порушенням. |
| Naming convergence | Структура вже вдала, але змінений модуль містить `handle`, `process`, `executeInternal` і синонімічні назви файлів. Виконай `plan` і потрібні `apply`, без `refine`. | Імена модуля, функцій, параметрів, результатів, файлів і основних викликачів узгоджені; назви описують намір та ефекти. Необхідний структурний недолік виправлено до перейменування. |
| Alternative designs | Для одного нетривіального правила можливі два правдоподібні власники з різною локальністю змін. Запусти `plan`. | До реалізації план показує два матеріально різні варіанти, проганяє через них ті самі сценарії й відому або обґрунтовано ймовірну зміну вимоги, пояснює вибір і відхилення іншого. |
| Overengineering | Простий stateless розрахунок без зовнішніх ефектів природно має одну функціональну форму. Виконай повний цикл. | Результат лишається простою функцією або малим модулем; немає DDD-об'єктів, портів чи interfaces без прихованої складності. Агент в одному реченні пояснює, чому архітектурні альтернативи були б штучними. Він не вигадує майбутні вимоги для виправдання абстракції. Незалежний перегляд явно перевірив цей ризик. |
| Деталізація й локальна свобода | Модуль має чітке правило, кількох викликачів і кілька рівноцінних способів організувати приватні типи. Запусти `plan`, потім `apply`. | План визначає власника, гарантії й потрібні міжмодульні операції; внутрішню декомпозицію залишено для реалізації, якщо вона не визначає гарантію. Агент обрав деталі без додаткового погодження чи повного повторного планування, зберіг контракт і перевірив поведінку. |
| Зворотний зв'язок до стратегії | Збережений план розділяє зміну залишку й запис резерву між незалежними операціями. Користувач погодив план і дозволив внутрішню перебудову, не фіксуючи структуру як обмеження. Під час `apply` перевірка відмови виявляє, що модель порушує підтверджену вимогу атомарності. | Агент назвав доказ, переглянув власність або контракт і оновив зачеплене рішення та залежні частини плану до поширення реалізації. Продовжив без зайвого питання; початкову гарантію зберіг і перевірив відмову. Незалежні рішення не перепланував. |
| Межа архітектурної свободи | Та сама знахідка потребує зміни структури, яку користувач явно зафіксував як обмеження. | Агент підготував конкретну зміну з наслідком і виніс її на рішення користувача; до відповіді залежну зміну не виконав. Локальні та незалежні зміни в межах дозволу продовжив. |
| Контракт із боку викликача | Нова реалізація приховує деталі добре, але повертає однаковий `null` для двох підтверджених наслідків, на які один із викликачів мусить реагувати по-різному. Запусти `apply`. | Перегляд охопив потрібного викликача, навіть поза текою зміненої реалізації. Результати стали розрізнюваними ідіоматичним способом; перевірено обидві реакції. Сторонні модулі не аудитувалися. |
| Життєвий цикл при скасуванні | Частина володіє підпискою та фоновою роботою. Успішний сценарій працює, але підтверджена вимога скасування потребує звільнення підписки й захисту від пізнього callback. Виконай повний цикл. | Явний власник забезпечує завершення на потрібних шляхах; перевірено скасування й пізній callback через доступний викликачу інтерфейс. Тести не закріплюють конкретні приватні поля або спосіб представлення стану. |
| Межі тактичних прийомів | Частина містить DTO, простий розрахунок, ідіоматичну операцію зміни стану з результатом і доменну гарантію, яку додатково забезпечує обмеження бази даних. Виконай повний цикл. | DTO й примітиви не отримали обгорток без правила, атомарну операцію не розділено заради формальної чистоти, обмеження бази збережено. Спосіб передавання помилок відповідає мові й проєкту. Кожна нова абстракція має конкретну потребу. |
| Завершення тактичного перегляду | Зачеплена реалізація й викликачі виконують критерії; існує інший рівноцінний стиль запису. | Агент завершив перевірений результат без вигаданих недоліків, заданої квоти знахідок чи повторних стилістичних проходів. Окремого звіту за кожним тактичним принципом не створено. |
| Без режиму | Виклич `$restrukt src/orders` без режиму. | Створено лише план; продуктовий код і тести не змінені, реалізація автоматично не почалась. |
| Одна задача | У плані дві доступні задачі (фікстура `one-task`). Виклич `apply` без назви, потім новим агентом повтори. | Кожен виклик виконав рівно одну задачу в порядку черги. Другий використав результат першої, не повторив її; як останній у черзі прийняв і записав рішення про незалежний перегляд коду. |
| Продовження однієї задачі | Є перервана задача з частковими правками й інша доступна. Виклич `apply` без назви. | Першою звірено й продовжено задачу з «Продовження»; сторонні правки збережені. Інша задача не виконувалась. |
| Незавершена залежність | Явно вибрана задача залежить від незавершеної; окремо перевір позначену готовою залежність із фактично зламаним контрактом (фікстура `broken-dependency`). | У першому випадку залежність не підхоплено автоматично. У другому залежність лишилась `готово`, з'явилась задача виправлення з причиною й посиланням на неї, обрану задачу переведено в `заблоковано` на ній. Обрану задачу не реалізовано на хибній передумові; наступний крок — задача виправлення. |
| Немає плану чи роботи | Виклич `apply` без плану; потім із усіма заблокованими задачами; потім із усіма готовими. | Відповідно: потреба в `plan`, конкретні перешкоди, потреба в `review` або наявний перевірений підсумок. Автоматичної перебудови немає. |
| Уже готова задача | Частина черги незавершена, але користувач явно обрав готову задачу. | Агент звірив її актуальність і завершив; не перейшов до іншої. Виявлена регресія повернула лише зачеплене в роботу. |
| Передача без чату | Новий агент має лише репозиторій і назву задачі з плану. | За посиланнями задачі він знаходить результат, правила, рішення, контракти попередників і перевірки. Не вгадує домовленостей і не відновлює всю історію. |
| Єдине знання | П'ять задач посилаються на один життєвий цикл; після планування уточнено його правило. | Правило має один основний запис. Видно залежні рішення й задачі; суперечливих копій немає. Зачеплені завершені задачі лишились `готово`; уточнення, що змінює їхній результат, стало новою задачею з причиною й посиланням на зачеплену. |
| Чесна гіпотеза | Архітектурний вибір залежить від непідтвердженої послідовності викликів; потрібний результат відомий. | Припущення позначено гіпотезою з доказом, який треба здобути, та залежними рішеннями. Перша доречна задача перевіряє його до поширення структури; воно не видане за вимогу. |
| Неясне приймання | Для однієї задачі невідомий потрібний результат, інша незалежна. | Перша заблокована конкретним питанням; друга доступна. План не оголошує всі задачі придатними до виконання через заповнені таблиці. |
| Якість декомпозиції | Початковий задум містить «створити сервіс», цикл залежностей і підготовчу задачу без споживача. | План переформулював задачі через завершений результат і перевірку, розв'язав цикл, включив підготовку до потрібного результату або обґрунтував окрему задачу. |
| Незалежний перегляд плану | Інший агент виконує `review plan`; у плані є непідтверджене рішення й прихована залежність. | Перевірено кодові докази, записано місце, наслідок і потрібне уточнення; залежні задачі заблоковано. Продуктовий код і тести не змінено; статус перевірки коду не підвищено, нова архітектура мовчки не обрана. |
| Зведення має виконавця | Дві реалізовані задачі лишили дубльоване рішення й тимчасовий міст. | У плані зведення й видалення закріплені за конкретною задачею. Звичайні виконавці не перебудовують весь застосунок; виконавець зведення перевіряє інтегроване ціле до review. |
| Незалежний перегляд коду | Усі задачі позначені готовими, локальні тести зелені, але викликачі двох задач несумісні при відмові. Новий агент виконує `review`. | Рев'ювер перевірив код від справжніх входів і знайшов наскрізне порушення. Код не редагував; записав доказ, наслідок і задачу виправлення. Ціле не позначено перевіреним. |
| Фінал після виправлення | Знахідку review усуває новий виконавець через `apply`, потім повторюється `review`. | Перевірено виправлення та вплив на залежні сценарії; незалежне не переписано. Завершення можливе лише з доказами потрібної поведінки й без обов'язкового залишку. |
| Актуальність фіналу | Після успішного review змінено перевірений код без нового commit; окремо повтори через `refine`. | Стан цілого скинуто до `очікує`; старий журнал не використано як новий доказ. Зачеплені задачі перевірені, потім потрібний актуальний review. |
| Status і незалежність | Усі задачі готові, але review не було (фікстура `all-done`); виклич `status`. Окремо автор коду виконує review сам. | Status не змінює файли й називає review наступною дією. Самоперевірка автора не названа незалежним переглядом. |
| Дрібне завдання | Однозначний запит на одну локальну зміну поведінки текстом у `implement`. | Короткий план із «Завданням» і критеріями; без паузи виконано одну задачу. Перевірка критерію спершу падала, потім пройшла через справжній вхід. Незалежних переглядів не запускали: причину пропуску й перевірки записано як самоперевірку; коміту немає. |
| Спека в теці й issue | `implement docs/specs/export/`; окремо `implement <GitHub issue>` з коментарем, що змінює вимогу. | Прочитано всі релевантні документи й коментар; критерії з джерела відділено від виведених. Недоступне джерело названо, завдання не вигадано. |
| Сесія питань | Спека має прогалину з різними наслідками для користувачів; відповідь відкриває нове доменне питання. | Питання поставлено пакетом до проєктування, з варіантами, наслідками й рекомендацією; сесія продовжилась до визначеного результату. Технічних деталей не питали. Відповіді записані як рішення з джерелом. |
| Вибір способу | Завдання розпадається на кілька задач; спосіб у запиті не названо. | Після плану показано стислий задум і три способи. «Покроково» завершив виклик без коду. Запит «виконай усе» наперед не спричинив повторного питання. |
| Оркестрація | Обрано оркестрацію для трьох задач. | Кожну задачу по черзі виконав новий помічник за циклом `apply`; план і журнал оновлював лише координатор після перевірки diff. Через кілька задач незалежний помічник зробив `review code`; знахідки виконано одним колом, змінене перевірено за новим рішенням про ризик. |
| Лише потрібне завданню | Нове правило в наявній моделі не має природного власника; поряд модуль із поганими іменами. | Першою йде переробка зачепленого зі збереженням поведінки, потім нова поведінка. Сусідній модуль не змінено, недолік записано в «Можливі доопрацювання». |
| Перегляд плану за потребою | Виклич `plan` з кількома задачами й непідтвердженою гіпотезою; окремо `implement` із кількома задачами. Збережи слід запусків. | Після перевірки придатності новий помічник без контексту виконав `review plan` і нічого не змінив. Основний агент записав знахідки як незалежний перегляд помічника, виправив план або обґрунтував незгоду; невирішене блокує залежні задачі. У `implement` це сталося до питання про спосіб. Без засобу запуску названо `review plan` у новому чаті, самоперевірку не видано за незалежну. |
| Останній `apply` | Покроковий план із трьох задач, одна змінює власника стану. Виклич `apply` тричі. | Перші два виклики перегляду не запускали. Третій після своєї задачі запустив незалежний `review code`; знахідки поставив задачами виправлення й назвав наступний `apply`, сам їх не виконував. Після задачі виправлення знову прийнято рішення щодо зміненого; «Перевірка цілого» має рядок `Автоматичне коло: закрите.`, друге коло не почалось. |
| Друге коло | Автоматичне коло закрите (перегляд помічника, виконане виправлення, перевірка зміненого), лишилась задача від перевірки зміненого. Виклич `apply`: окремо з рядком `Автоматичне коло: закрите.` і зі старим вільним текстом без нього (фікстура `second-circle-marked`, `second-circle`). | Задачу виконано; помічника не запущено, рішення про перегляд і самоперевірки цілого немає; «Перевірка цілого» не `перевірено`, наступний `review` — на вибір користувача. У старому плані коло розпізнано за записаними фактами. |
| Інший план в `implement` | У `docs/restrukt/` є незавершений план перебудови того самого обсягу. | `implement` створив окрему теку, не читав і не змінив наявний план. |
| Продовження `implement` | Після паузи користувач повертається в новому чаті з `implement <назва плану>`. | Робота відновлена з «Продовження» з обраним способом; готові задачі не повторено. |

Якість архітектури оцінюй за [критеріями](../skills/restrukt/references/architecture.md) на фактичному коді. Перевірка пакета — `python3 scripts/check_plugin.py`; нативна перевірка Claude Code — `claude plugin validate .`.
